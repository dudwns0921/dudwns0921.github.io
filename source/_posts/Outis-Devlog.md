# 게임 소개

Outis는 호메로스의 『오디세이아』 중 키클롭스 에피소드를 바탕으로 만든 3인칭 어드벤처 게임이다. 제목은 오디세우스가 외눈 거인 폴리페모스에게 댄 가짜 이름으로, "아무도 아니다"라는 뜻을 가지고 있다.

| | |
|---|---|
| 장르 | 3인칭 어드벤처 |
| 엔진 | Godot 4.7 |
| 사용 도구 | Claude Code, Godot MCP Pro, Meshy AI, ElevenLabs, ChatGPT |
| 배포 | itch.io (Windows, macOS / 한국어, English) |

치즈를 훔쳐 먹다 들킨 오디세우스와 선원 열두 명이 거인의 동굴에 갇히고, 거인은 저녁마다 선원을 둘씩 잡아먹는다. 플레이어는 선원이 다 먹히기 전에 잠든 거인 곁을 몰래 오가며 무기를 만들어 탈출해야 한다.

진행 순서는 원작을 그대로 따라갔다.

```
몽둥이 잘라내기 → 다듬기 → 선원 풀기 → 불 살리기 → 달구기 → 눈 찌르기 → 탈출
```

탈출한 뒤에는 배 위에서 거인에게 진짜 이름을 외칠지 말지를 고르게 되고, 이 선택에 따라 엔딩이 갈린다.

# 어떻게 만들었나

## 역할 분담

구현은 AI가, 기획과 에셋은 내가 맡았다. 도구는 해커톤 때와 마찬가지로 Claude Code와 Godot MCP Pro를 사용했다.

| | |
|---|---|
| 기간 | 09-10 첫 커밋 ~ 09-28 0.1.1 배포 |
| 커밋 | 130개 |
| 코드 | GDScript 약 11,600줄, 테스트 약 3,800줄 |
| 기획서 | GDD 804줄 |

## GDD와 코드 동기화

해커톤 때 가장 불편했던 점은 GDD와 코드가 따로 논다는 것이었다. 회의할 때마다 GDD를 고쳤는데, 코드에 반영이 됐는지는 직접 플레이해 보기 전까지 알 수가 없었다. 이틀짜리 프로젝트라 어떻게든 넘어갔지만, 기간이 길어지면 분명히 문제가 될 거라고 생각했다.

그래서 이번에는 첫날에 `gdd-sync`라는 스킬부터 만들었다. 원리는 간단한데, GDD와 코드 양쪽에 같은 ID를 붙여두는 것이다.

GDD 맨 뒤에 아래와 같은 표를 두고,

```markdown
| ID | 값 | 출처 | 코드 위치 | 상태 |
|---|---|---|---|---|
| BAL.CREW.START | 12 | 4.3 | game/config/balance.gd:CREW_START | 동기 |
| BAL.CREW.FREE_SEC | 4 | 4.5 | game/config/balance.gd:CREW_FREE_SEC | 동기 |
```

코드에서는 해당 값을 정의하는 줄에 주석으로 ID를 적어둔다.

```gdscript
static var CREW_START := 12  # GDD: BAL.CREW.START
static var CREW_FREE_SEC := 4.0  # GDD: BAL.CREW.FREE_SEC
```

스킬을 실행하면 파이썬 스크립트가 표와 주석을 대조해서 값이 다른 항목, 아직 구현되지 않은 항목, 표에는 없는데 코드에만 있는 항목을 찾아준다. 그리고 `/gdd-sync to-code`를 실행하면 GDD를 기준으로 코드를 고치고, `/gdd-sync to-gdd`를 실행하면 반대로 코드를 기준으로 GDD를 고친다.

최종적으로 이 표에는 253개 항목이 들어갔다. 만드는 동안 순서가 바뀌기도 하고 아이템이 통째로 빠지기도 했는데, 그때마다 문서와 코드가 같이 바뀌어서 기획서를 끝까지 믿고 볼 수 있었다.

## 밸런스 조정

게임을 만들면서 가장 시간이 많이 든 건 밸런스였다. 값을 바꾸고, 플레이해 보고, 다시 바꾸는 과정을 계속 반복해야 하는데 그때마다 Claude에게 "달리기 소음을 8에서 6으로 바꿔줘"라고 요청하는 건 너무 번거로웠다.

고민 끝에 밸런스 수치 111개를 엑셀 파일로 빼기로 했다. 엑셀에서 값을 고치고 저장하면 실행 중인 게임이 0.5초 안에 파일을 다시 읽어서 바로 반영한다. 덕분에 게임을 켜둔 채로 값을 바꿔가며 테스트할 수 있게 되었다.

xlsx 파일은 사실 XML을 zip으로 묶은 것이라, 별도 라이브러리 없이 Godot에 내장된 `ZIPReader`와 `XMLParser`만으로 읽을 수 있었다.

![밸런스 표](balance-xlsx.png)

값이 확정되면 엑셀의 값을 코드에 반영하고, 위에서 만든 `gdd-sync`로 GDD까지 맞추는 흐름이다.

## 동굴 만들기

동굴은 내가 종이에 그린 스케치에서 시작했다. 입구, 침상, 모닥불 정도만 그려서 넘겼고 나머지는 Claude가 GDD에 맞춰 채웠다.

![위에서 본 동굴](map-topdown.png)

특이한 점은 동굴 씬 파일을 직접 수정하지 않는다는 것이다. 파이썬 스크립트에 좌표를 적어두고, 스크립트를 실행하면 씬 파일이 만들어지는 구조다.

```python
FIRE = (5.5, -4.0)  # 거인 손 범위 밖(7.1 m). 침상까지 약 10 m
CHOPPING_ROCK = (5.0, 6.0)
```

처음에는 굳이 이렇게까지 해야 하나 싶었는데, 만들다 보니 오브젝트의 위치가 곧 밸런스라는 걸 알게 되었다. 예를 들어 몽둥이를 다듬는 바위는 원래 거인에게서 34m 떨어진 곳에 있었다. 그런데 플레이해 보니 토막을 아무리 천천히 끌고 가도 도착하기 전에 거인이 깨어났다. 거리를 17m로 줄이고 나서야 해결됐다. 좌표가 코드로 관리되니 이런 조정을 하기가 수월했다.

## 거인

![모닥불 너머의 거인](cave-fire.png)

거인은 이 게임에서 가장 공을 들인 부분이다. 처음에는 거인이 동굴을 돌아다니며 플레이어를 찾는 방식을 생각했지만, 구현 난이도도 높고 무엇보다 원작의 거인과 어울리지 않는다고 생각했다. 그래서 거인은 침상 옆에 앉아서 졸고 있고, 대신 소리와 시야, 손으로 플레이어를 압박하게 했다.

### 소음

플레이어가 움직이면 소음이 쌓인다. 달리면 많이 쌓이고, 걸으면 조금 쌓이고, 웅크리면 쌓이지 않는다. 거인과의 거리에 따라서도 달라져서 가까울수록 더 많이 쌓인다.

```gdscript
scale *= Balance.noise_distance_scale(d)      # 6m 안 x2, 18m 밖 x0.5
if fire_lit():
	scale *= Balance.FIRE_LIT_NOISE_SCALE     # 불이 켜져 있으면 x1.35
```

소음이 일정 수준을 넘으면 거인이 눈을 뜨고, 가득 차면 일어나서 선원 둘을 잡아먹는다.

원래는 소음 게이지가 화면에 표시됐는데 나중에 뺐다. 게이지가 있으니 거인은 안 보고 게이지만 보게 되었기 때문이다. 지금은 거인이 눈을 뜨거나 투덜대는 걸 보고 판단해야 한다.

### 시야와 손

거인은 외눈이라 원근감이 나쁘다는 설정을 넣어서, 가만히 있는 건 못 보고 움직이는 것만 보게 했다. 그래서 거인이 이쪽을 볼 때 멈춰 있으면 들키지 않는다.

거인 가까이 가면 손에 잡혀 죽는다. 그런데 몽둥이가 거인 바로 옆에 있어서, 가까이 가는 것만으로 죽게 하면 진행 자체가 불가능했다. 그래서 거인이 졸고 있을 때는 2초 이상 계속 움직여야 잡히도록 했다. 몽둥이를 자르는 데 6초가 걸리니, 조금 자르고 멈추는 걸 여러 번 반복해야 한다.

![잡히기 직전](danger.png)

잡히기 직전에는 화면 가장자리가 붉어지고 심장 소리가 난다. 이 심장 소리는 처음에 너무 저음으로 만들어서 노트북 스피커에서는 아예 들리지 않았고, 몇 번을 다시 만들어야 했다.

## 하루

처음 버전에는 시간 제한이 없었다. 소리만 안 내면 얼마든지 기다릴 수 있었고, 플레이해 보니 긴장감이 전혀 없었다. 그래서 원작처럼 하루 단위로 시간이 흐르게 바꿨다.

```
저물녘 → 저녁 식사 → 밤 → 새벽 → 낮 → 귀가
```

거인은 저녁마다 선원 둘을 먹고 잠들고, 새벽이 되면 양을 몰고 나갔다가 저물녘에 돌아온다. 눈을 찌를 수 있는 건 거인이 깊이 잠든 밤뿐이다.

![양을 몰고 나가는 거인](dawn.png)

거인이 걸어 다니게 되면서 애니메이션 문제가 생겼다. Meshy에서 받은 애니메이션에는 앉아 있는 동작과 걷는 동작만 있어서, 앉아 있다가 걷기 시작하면 거인이 순간적으로 튀어 올랐다. 급한 대로 두 동작의 중간 자세를 코드로 계산해서 일어서는 동작을 만들어 넣었고, 나중에 제대로 된 애니메이션을 받아서 교체했다.

## 선원

선원은 플레이어가 조종할 수 없게 했다. 우리에서 풀어주면 알아서 숨을 곳으로 걸어가는데, 걸어가는 동안 소리를 낸다. 가끔은 거인을 보고 놀라서 펄쩍 뛰기도 한다.

조종할 수 있게 하는 편이 구현도 쉽고 플레이하기도 편했을 것이다. 하지만 그렇게 되면 선원은 단순히 말뚝을 드는 도구가 될 것 같았다. 한 명씩 풀고 기다릴지, 한꺼번에 풀고 위험을 감수할지 고민하게 만들고 싶었다.

![말뚝 달구기](heat.png)

말뚝을 달구는 부분은 원래 E키를 20초 동안 누르고 있는 방식이었다. 플레이해 보니 너무 지루해서 타이밍에 맞춰 세 번 뒤집는 방식으로 바꿨다.

## 에셋

### 캐릭터

캐릭터는 컨셉 이미지를 먼저 만들고, Meshy AI로 3D 모델을 생성했다.

![폴리페모스 컨셉](concept-polyphemus.png)

여기서 재밌는 문제가 하나 있었다. 거인은 외눈인데, Meshy가 눈 하나 안에 눈동자를 두 개 그려놓은 것이다. 아마 사람 얼굴을 기준으로 학습되어서 그런 것 같다. Blender로 직접 고칠까도 생각했지만, 결국 파이썬 스크립트로 눈 부분의 텍스처를 감은 눈으로 덮어버리고 뜬 눈은 게임에서 따로 붙이는 방식으로 해결했다.

### 컷신

컷신은 고대 그리스 도자기 그림 스타일로 만들었다. 이 이야기를 호메로스가 노래로 전한다는 설정이라, 후대에 도자기에 그려진 장면처럼 보이면 어울리겠다고 생각했다.

![오프닝 컷신](cutscene-intro.png)
![찌르기 컷신](cutscene-stab.png)

Claude로 프롬프트를 만들고 ChatGPT로 이미지를 생성했다. 가장 어려웠던 건 열두 장의 그림체와 인물을 일정하게 유지하는 것이었는데, 공통 스타일과 인물 묘사를 따로 정리해두고 매번 똑같이 붙여 넣는 방식으로 어느 정도 해결할 수 있었다.

동굴 안쪽에는 먼저 갇혔던 사람들이 남긴 흔적이 숨겨져 있는데, 이 그림들도 같은 방식으로 만들었다.

![안쪽 동굴](inner-cave.png)

### 사운드

효과음은 대부분 ElevenLabs와 무료 음원을 사용했고, 배경음악이나 불 소리 같은 일부는 파이썬으로 합성했다.

한 가지 밝히자면 거인의 코골이는 내 코골이다. 마음에 드는 소리를 찾지 못해서 직접 녹음한 뒤 느리게 재생했더니 생각보다 그럴듯했다.

## 테스트

코드를 직접 보지 않다 보니 제대로 동작하는지 확인할 방법이 필요했다.

먼저 기능별로 테스트 씬을 만들어서 화면 없이 실행할 수 있게 했다. 현재 18개가 있고, 배포 전에 자동으로 실행된다.

색감처럼 눈으로 봐야 하는 부분은 정해진 위치에서 스크린샷을 찍는 씬을 따로 만들었다. 이 글에 들어간 게임 화면도 이 씬으로 찍은 것이다.

![불이 꺼진 동굴](cave-dark.png)

그리고 치트 콘솔을 넣어서 원하는 단계로 바로 넘어갈 수 있게 했다. 눈 찌르기 부분을 수정할 때마다 처음부터 15분씩 플레이할 수는 없었기 때문이다.

## 삽질

만들면서 시간을 많이 쓴 문제들도 있었다.

가장 기억에 남는 건 Godot 에디터를 켜둔 상태에서 터미널로 임포트 명령을 실행했을 때다. 임포트 과정에서 프로젝트 설정 파일이 덮어써지면서 MCP 관련 설정이 지워졌고, 그 뒤로 MCP 도구가 전부 타임아웃이 났다. 원인을 찾는 데 30분이 걸렸다.

또 하나는 새로 만든 클래스를 Godot 에디터가 인식하기 전에 게임을 실행하면, 전혀 상관없는 곳에서 에러가 난다는 것이었다. 이 문제는 CLAUDE.md에 적어둬도 계속 반복되어서, 결국 파일을 저장할 때마다 확인하는 훅을 만들어서 해결했다.

# 회고

## 잘한 점

GDD 동기화를 가장 먼저 만든 건 잘한 결정이었다고 생각한다. 만드는 내내 기획이 계속 바뀌었는데, 문서가 항상 최신 상태라 헷갈릴 일이 없었다.

밸런스 값을 엑셀로 뺀 것도 좋았다. 코드는 전부 맡겼지만 숫자만큼은 내가 직접 만지고 싶었고, 실제로 플레이하면서 바로바로 고칠 수 있어서 작업 속도가 많이 빨라졌다.

## 아쉬운 점

그래픽이 가장 아쉽다. 캐릭터는 그럭저럭 나왔는데 동굴 자체는 아직 많이 밋밋하다.

그리고 게임을 처음 시작했을 때 뭘 해야 하는지 알기 어렵다. 지금은 화면에 글로 목표를 알려주고 있지만, 글을 읽지 않아도 자연스럽게 알 수 있도록 만들었어야 했다.

# 마치며

해커톤 때는 40시간이라는 제한이 있었기 때문에 어떻게든 끝낼 수 있었다. 이번에는 끝을 내가 정해야 했는데, 고치고 싶은 부분이 계속 보여서 오히려 더 어려웠던 것 같다. 결국 0.1이라는 버전을 붙여 일단 올리고 나서야 한숨 돌릴 수 있었다.
